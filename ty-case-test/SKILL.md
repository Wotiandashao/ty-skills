# 测试用例 XMind 生成

## 核心职责

将需求内容拆解为可执行、可观察、可判断的测试用例，并在需要时通过 `scripts/generate_xmind.py` 生成 XMind 文件。

本 skill 的主链路是：

1. 读取或提取需求内容。
2. 分析业务对象、页面入口、角色权限、状态流转、配置项、接口和数据规则。
3. 识别端信息并先按端拆分。
4. 在每个端下拆分功能模块和测试场景。
5. 生成结构化测试用例 JSON。
6. 调用脚本生成 `.xmind`。
7. 验证 `.xmind` 结构并清理临时 JSON。
8. 向用户说明覆盖范围和最终交付文件。

## 适用范围

使用本 skill 处理：

- 根据需求文档或需求文本生成测试用例。
- 根据 Word 文档提取出的需求内容生成测试用例。
- 根据 H5、网页或原型页面中的需求信息提取测试点。
- 将测试用例输出为 XMind、思维导图、测试用例树或 `.xmind` 文件。
- 补充异常、边界、缓存、权限、兼容性、数据异常等测试场景。

不要使用本 skill 处理：

- 普通思维导图整理。
- 非 QA 测试场景的需求总结。
- 不需要测试用例结构的简单问答。
- 与测试用例无关的 XMind 编辑任务。

## 输入来源处理

- 纯文本需求：直接分析正文。
- Word 需求：先使用运行环境可用的文档读取能力提取正文，再进入本流程。
- H5 或网页需求：先使用浏览器、网页读取或用户提供的页面内容获取需求正文，再进入本流程。
- 无法读取的链接或受权限保护的页面：请用户提供可访问文本或截图中的关键需求信息。

`scripts/generate_xmind.py` 只负责“结构化 JSON -> XMind 文件”，不负责直接解析 Word 或抓取网页。

## 中间产物管理

结构化 JSON 是生成 XMind 的脚本输入，默认只作为临时中间产物使用，不作为最终交付物保留。

执行时必须遵循：

- 生成 `.xmind` 前可以在项目 `TEMP` 目录临时生成结构化 JSON。
- JSON 默认视为临时中间产物；除非用户明确要求查看、保留或复核 JSON，否则不要在最终交付中保留 JSON。
- 生成并验证 XMind 成功后，必须删除本次生成的临时 JSON。
- 如果用户明确要求保留 JSON，必须将 JSON 放在项目 `TEMP` 目录，并在最终回复中说明 JSON 路径、用途和保留原因。
- 如果临时 JSON 删除失败，必须在最终回复中说明未清理路径、失败原因和建议处理方式。
- 最终回复默认只交付 XMind；只有用户明确要求时才同时交付 JSON。

## 多端拆分规则

当需求正文显式提到端名时，必须先按端拆分测试用例，不能把不同端合并成同一条用例。标准端标签为：

- `iOS`
- `Android内发包`
- `Android外发包`
- `Android`
- `小程序`
- `H5`

执行时必须遵循：

- 需求里点名的端，每个端单独建一级分组。
- 即使业务流程看起来一致，也要分别生成该端自己的用例。
- 当需求已点名多个端时，共性场景也要分别落到每个已识别端下面，不生成一条通用 case。
- 如果同一需求里同时出现 `Android内发包`、`Android外发包` 和笼统的 `Android`/`安卓` 表述，则笼统 Android 场景默认同时分摊到内发包和外发包，除非原文明确限制。
- 端名称优先使用需求原文，再统一映射到标准端标签；不要自行发明模糊分组名。

## 标准执行流程

1. 确认输入类型和目标产物。
   - 若用户明确要 `.xmind`，最终必须生成文件。
   - 若用户只要用例文本，可输出结构化 Markdown，同时说明可继续生成 XMind。
2. 提取需求事实。
   - 识别页面、入口、用户角色、业务动作、状态、配置、接口、数据来源、限制条件。
   - 区分明确需求、推断需求和缺失信息。
3. 识别端信息并确定分组结构。
   - 若需求显式提到 `iOS`、`Android内发包`、`Android外发包`、`Android`、`小程序`、`H5` 等端名，先按端拆分。
   - 多端需求默认采用 `项目 -> 端 -> 业务模块 -> 用例` 结构。
   - 未显式提到端时，可继续使用单层 `项目 -> 模块 -> 用例` 结构。
4. 在端下拆分模块。
   - 简单需求按功能模块划分。
   - 复杂需求按功能域、子模块、功能点划分。
5. 构建测试场景矩阵。
   - 先覆盖需求文档中明确描述的测试点。
   - 再基于模块、入口、状态、数据、接口、角色、配置等上下文适度发散补充场景。
   - 发散场景应标注为“补充场景”或在汇报中说明来源，避免和明确需求混淆。
   - 默认覆盖正常流程、异常流程、边界值、数据异常、网络异常和缓存场景。
   - 按需求增加权限、兼容性、埋点、安全、并发等场景。
6. 生成结构化 JSON。
   - 遵循“结构化数据格式”中的 schema。
   - JSON 是生成 XMind 的临时输入，默认不作为最终交付物。
   - 不输出用例编号、优先级或标签。
7. 生成 XMind。
   - 使用 `scripts/generate_xmind.py --input <json> --output <xmind>`。
   - 生成前校验输入，生成后校验 XMind 包结构。
8. 清理中间产物。
   - 若用户未明确要求保留 JSON，生成并验证 XMind 成功后删除本次生成的临时 JSON。
   - 若用户明确要求保留 JSON，在最终回复中说明 JSON 路径、用途和保留原因。
   - 若删除临时 JSON 失败，在最终回复中说明未清理路径和失败原因。
9. 汇报结果。
   - 默认只给出 XMind 输出文件路径。
   - 简述端数、模块数、用例数、主要覆盖维度和未覆盖风险。

## 缺失信息处理

只有在缺失信息会直接改变测试用例方向时才向用户提问。常见可直接假设：

- 未提供平台时，按通用客户端或网页场景覆盖。
- 未提供账号角色时，覆盖未登录、已登录、登录过期和无权限。
- 未提供接口细节时，覆盖成功、空数据、失败、超时、异常字段。
- 未提供兼容范围时，覆盖主流 iOS、Android、H5 或桌面浏览器，按需求上下文取舍。

在输出中把重要假设标明为“假设”或“待确认”。

## 结构化数据格式

生成 XMind 前，将测试用例整理为以下 JSON。

### 多端结构

```json
{
  "project_name": "搜索功能测试用例",
  "platforms": [
    {
      "name": "iOS",
      "modules": [
        {
          "name": "入口",
          "cases": [
            {
              "title": "验证首页搜索入口展示",
              "purpose": "验证 iOS 端首页顶部搜索入口按配置正常展示",
              "prerequisites": ["后台已配置暗纹词"],
              "steps": ["打开 iOS 端 App 并进入首页", "查看页面顶部搜索区域"],
              "expected": ["页面顶部展示搜索框", "搜索框旁展示购物车和消息入口"]
            }
          ]
        }
      ]
    }
  ]
}
```

### 旧版兼容结构

```json
{
  "project_name": "搜索功能测试用例",
  "modules": [
    {
      "name": "入口",
      "cases": [
        {
          "title": "验证首页搜索入口展示",
          "purpose": "验证首页顶部搜索入口按配置正常展示",
          "prerequisites": ["后台已配置暗纹词"],
          "steps": ["进入首页", "查看页面顶部搜索区域"],
          "expected": ["页面顶部展示搜索框", "搜索框旁展示购物车和消息入口"]
        }
      ]
    }
  ]
}
```

字段规则：

- `project_name`：必填，XMind 根主题。
- `platforms[].name`：多端结构必填，端名称。
- `platforms[].modules[].name`：多端结构必填，业务模块名称。
- `modules[].name`：旧版兼容结构必填，模块名称。
- `cases[].title`：必填，用例标题，仅用于结构化数据可读性，不输出到 XMind。
- `cases[].purpose`：必填，测试目的。
- `cases[].steps`：必填，非空数组。
- `cases[].expected`：必填，非空数组。
- `cases[].prerequisites`：可选，数组或字符串；为空时输出 `前置条件：无`。
- 顶层 `platforms` 与 `modules` 不允许同时存在；同时存在时直接报错，避免结构歧义。

## XMind 节点结构

多端需求推荐输出结构：

```text
项目名称
├── iOS
│   ├── 入口
│   │   ├── 测试目的：...
│   │   │   └── 前置条件：...
│   │   │       └── 测试步骤：
│   │   │           1、...
│   │   │           2、...
│   │   │           └── 预期结果：
│   │   │               1、...
│   │   │               2、...
│   │   └── ...
│   └── 异常场景
└── Android内发包
    └── 入口
```

未显式提到端时，仍可使用旧版兼容结构：

```text
项目名称
├── 模块
│   ├── 测试目的：...
│   └── ...
└── ...
```

XMind 不输出用例编号、优先级、标签或备注节点。每条用例的展示顺序固定为：`测试目的 -> 前置条件 -> 测试步骤 -> 预期结果`。`测试步骤` 和 `预期结果` 应作为节点内多行文本展示，不拆成多个子节点。

## 用例质量标准

每条用例必须满足：

- 可执行：步骤是用户、系统或测试人员可以实际操作的动作。
- 可观察：结果能在界面、接口、日志、数据或状态中被观察。
- 可判断：预期结果有明确通过条件。
- 单一目的：一条用例验证一个核心目标，避免混入多个无关功能。
- 步骤对应：预期结果与步骤序号或关键动作对应。
- 粒度一致：同一模块内用例颗粒度保持一致。
- 多端隔离：不同端的场景必须各自成条，不得把多个端揉进同一条用例。

避免写法：

- “功能正常”
- “符合预期”
- “查看是否正常”
- “接口异常时处理正确”
- “页面展示正确”
- “验证 iOS/Android/小程序搜索入口展示一致”

推荐写法：

- “接口返回空数组时，页面展示空态文案，并隐藏分页控件。”
- “登录过期后点击搜索按钮，跳转登录页；登录成功后回到搜索页并保留输入内容。”
- “验证 Android外发包首页顶部搜索入口按配置正常展示。”

## 测试点发散规则

生成测试用例时，先覆盖需求文档中明确描述的测试点，再根据业务上下文适当发散补充测试场景。发散场景应围绕当前需求相关的模块、入口、状态、数据、接口、配置、权限和用户路径展开，优先补充可能影响用户体验、数据正确性或稳定性的场景。

发散时必须遵循：

- 不脱离需求范围，不凭空扩展无关业务。
- 每个补充场景都要能说明触发条件、操作步骤和预期结果。
- 优先补充异常、边界、空态、弱网、缓存、权限、兼容性、重复操作、状态切换、接口失败和数据异常。
- 对需求未明确但合理推断的场景，在最终覆盖说明中标记为“补充场景”或“基于需求推断”。
- 多端需求中，补充场景也要分别分摊到每个显式端下，不能只写一条通用补充用例。

## 测试场景矩阵

默认考虑：

| 维度 | 覆盖内容 |
| --- | --- |
| 正常流程 | 主路径、关键入口、成功提交、成功展示 |
| UI 展示 | 文案、图标、按钮、空态、加载态、错误态 |
| 交互行为 | 点击、输入、切换、返回、刷新、重复操作 |
| 业务规则 | 配置开关、命中条件、状态流转、排序规则 |
| 数据场景 | 空数据、单条、多条、大量、重复、异常字段 |
| 网络接口 | 成功、失败、超时、弱网、断网、重试 |
| 缓存逻辑 | 首次进入、有缓存、缓存过期、清除缓存 |
| 边界值 | 0、1、最大值、超长、特殊字符 |

按需求启用：

| 维度 | 启用条件 |
| --- | --- |
| 权限角色 | 涉及登录、角色、会员、后台配置或资源权限 |
| 兼容性 | 涉及多端、H5、小程序、浏览器或不同屏幕 |
| 并发一致性 | 涉及多端同时操作、库存、订单、状态同步 |
| 安全风控 | 涉及敏感词、越权、注入、隐私或支付 |
| 埋点日志 | 需求明确提到曝光、点击、转化或数据分析 |

## 输出要求

交付 `.xmind` 时，同时说明：

- XMind 文件路径。
- 端数、模块数和用例数。
- 覆盖的测试维度。
- 关键假设和待确认项。
- 默认不交付结构化 JSON；只有用户明确要求查看、保留或复核 JSON 时，才说明 JSON 文件路径、用途和保留原因。
- 若临时 JSON 未能删除，说明未清理路径和失败原因。
- 生成或验证失败时的错误原因。

## 资源

- `scripts/generate_xmind.py`：将结构化测试用例 JSON 生成 XMind 文件，并执行输入和输出验证；调用脚本所需 JSON 默认是临时中间产物，验证成功后应按“中间产物管理”清理。
- `references/xmind_template.md`：测试用例树结构、示例、场景矩阵和写作规范参考。需要补充复杂样例或检查用例格式时读取。
- `examples/sample_cases.json`：可直接用于生成 XMind 的示例输入。
- `examples/sample_requirement.md`：需求片段到用例拆解的示例材料。
