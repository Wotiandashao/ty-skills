# 开发规划规则

本文件提供 `$ty-dev-plan` 的详细执行规则。生成或更新规划文件时阅读；仅判断 skill 是否适用时不必加载。

## 1. 输入与证据

### 1.1 确定输入

确认以下信息：

- 原始需求文档及其格式。
- 目标项目与适用的项目规范。
- 规划文件输出位置。
- 已有实施计划或执行步骤文件（如有）。
- 实施计划当前审核状态，以及用户是否明确要求生成执行步骤。

能从会话、项目或已有计划确定的信息不要重复询问。输出位置按以下顺序选择：用户明确指定的位置、项目已有约定、项目根目录下的 `docs/需求/{需求标识}/`。

原始需求是输入证据。不要生成新的需求说明文档，也不要擅自修改、覆盖或规范化原始需求文件。

### 1.2 读取不同格式

- Markdown：读取正文，并检查影响需求理解的相对链接、图片和附件是否可访问。
- DOCX：使用当前环境可用的文档读取能力提取正文和表格；图片、批注或修订会影响含义时必须核实。
- DOC：先识别真实格式，再使用环境已有的兼容读取或转换能力。需要转换时只在项目 `TEMP` 中创建副本，不覆盖原文件。
- 转换或解析失败：说明具体限制，请用户提供 DOCX 或 Markdown；不要宣称已完整读取。
- 关键图片、段落、表格或附件无法访问：记录为信息缺口，不得假定其中没有需求。

不要因扩展名相似而把 DOC 当作 DOCX。解析成功也不等于内容完整，应检查正文、表格及影响范围的视觉内容。

### 1.3 证据分类

在调研和文档中区分：

- 原文要求：来自需求文档或用户明确说明，使用原文编号或可定位引用。
- 已核实事实：来自实际代码、配置、测试或项目文档，附路径或其他证据。
- 建议方案：基于要求与事实形成的设计选择，说明理由。
- 假设：尚未确认但可暂时采用的可逆判断，明确影响。
- 待确认事项：会影响范围、业务规则、数据设计或总体方案的问题。

没有可访问的目标项目时，可以生成明确标注为概念性草稿的计划，但不得编造现有模块、文件路径、命令或验证结果。

## 2. 项目调研与澄清

先读取适用的项目指令、相关目录、核心实现、接口和测试约定。只调研与需求有关的范围；不要顺手修改业务代码或无关文件。

仅集中询问会改变功能范围、业务规则、数据设计或总体方案的关键问题。可逆细节可以采用有依据的建议，但必须写入假设。等待关键答案时继续调研不受影响的部分。

关键问题未解决时：

- 受影响章节标记为草稿或阻塞。
- 对应步骤写明启动条件和阻塞原因。
- 不得声称整套规划已具备直接执行条件。

需求有编号时沿用原编号；没有编号时，可在实施计划中建立轻量引用编号，并映射到章节、标题、表格行或简短内容摘要。不要为编号另建需求文档。

## 3. 两阶段交付与审核门禁

### 3.1 第一阶段：只生成实施计划

首次处理一个需求时，只创建或更新唯一的 `{需求名}-实施计划.md`。不得同时创建执行步骤文件，即使需求和项目上下文已经完整。

实施计划完成后：

- 将文档状态设为“待审核”。
- 将执行步骤生成状态设为“未生成（待审核）”。
- 给出拟拆分的步骤范围、顺序、启动条件和依赖，但不创建执行步骤文件、不添加无效链接、不分配正式任务编号。
- 只向用户交付实施计划，指出重点审核项和待确认内容，然后停止。

用户要求评审、补充、修订或继续完善实施计划时，仍停留在第一阶段。每次实质修改后重新标记为“待审核”。

### 3.2 审核通过的判定

只有用户明确表达以下两层意图时，才进入第二阶段：

1. 最新实施计划已经审核通过。
2. 现在需要根据该计划生成执行步骤。

不得根据以下情况推断审核通过：

- 用户没有提出异议。
- 实施计划内容看起来完整。
- 用户只说“继续”“完善”“修改这里”或提出评审意见。
- 项目中已经存在旧执行计划或旧执行步骤文件。

如果用户明确审核通过但没有要求生成执行步骤，记录审核状态并等待；如果用户要求生成执行步骤但无法确认实施计划是否已审核通过，先请求确认审核结果。

### 3.3 第二阶段：生成执行步骤

进入第二阶段时：

1. 重新读取最新实施计划，不能依赖审核前的会话记忆。
2. 识别用户在审核中直接修改或补充的内容，并将其视为最新方案的一部分。
3. 核对相关项目事实是否发生变化；有冲突时说明，不擅自改写已审核方案。
4. 按实施计划中的步骤建议和实际依赖，为每个正式任务生成一个独立执行步骤文件。
5. 更新实施计划中的执行步骤索引、正式任务编号、覆盖关系和生成状态。
6. 连续生成本阶段所需的全部执行步骤文件，不逐文件重复请求授权。

## 4. 唯一实施计划与命名

每个需求只维护一个主实施计划，命名为 `{需求名}-实施计划.md`。需求名应来自用户需求或需求标识；用于文件名时清理 `/ \ : * ? " < > |` 等非法字符，但正文保留完整需求名称。

实施计划必须包含：

1. 文档状态、需求来源、目标项目和可获得的调研基准。
2. 实施目标、包含范围和明确不包含的内容。
3. 项目现状、相关实现、约束和可复用能力，附已核实路径。
4. 推荐技术方案、关键决策和理由；只在存在实质选择时讨论替代方案。
5. 模块及文件变更、接口与数据变化、关键业务流程及适用的异常和边界处理。
6. 按需求实际需要补充的兼容、迁移或回退安排。
7. 验证策略和可观察的验收依据。
8. 假设、风险和待确认事项。
9. 第一阶段记录执行步骤生成建议、范围、依赖和推荐顺序；第二阶段更新为实际文件索引。
10. 第一阶段记录需求到实施方案、拟执行范围及验证方式的覆盖关系；第二阶段补充正式执行步骤编号和链接。

路径必须标明证据状态：已存在且核实的路径直接引用；计划创建的路径写成“拟新增”；不能确认的位置写成“待核实”并说明原因。

实施计划状态使用“待审核 / 审核通过 / 已替代”。另行记录执行步骤生成状态：“未生成（待审核）/ 待生成（已审核）/ 已生成 / 需重新生成”。第一阶段不能因为尚无执行步骤文件而把实施计划标为不完整。

已有实施计划时先完整读取，保留用户手工补充和仍有效的结论，在原文件上定向修订。不要默认创建“最终版”“最终版2”等并行主文档。

## 5. 执行步骤拆分与文件命名

### 5.1 是否拆分

执行步骤不是一个包含任务清单的总文件。第二阶段按独立交付边界、依赖关系和独立验收能力拆分任务，每个正式任务生成一个文件。

不要按固定任务数强行拆分，也不要机械地按前端、后端拆分。共同完成或共同验证的紧密耦合动作可以放在同一个步骤中。可并行的步骤只标注，不自动启动子智能体。

### 5.2 文件名规则

- 实施计划：`{需求名}-实施计划.md`。
- 执行步骤：`{需求名}-任务-T01-执行步骤.md`、`{需求名}-任务-T02-执行步骤.md` 等。
- 任务编号在整个需求范围内唯一，使用 `T01`、`T02` 等格式。
- 同一需求的所有文件使用同一需求名；文件名非法字符按第 4 节规则清理。
- 文件名中的任务编号必须与文件正文中的任务编号一致。
- 不生成 `执行计划.md` 或 `执行计划-01-xxx.md` 作为新的正式产物。

### 5.3 每项执行步骤的最低信息

| 字段 | 规则 |
| --- | --- |
| 任务编号 | 整个需求范围内唯一，例如 `T01`；不依赖文件名区分 |
| 任务名称 | 说明本步骤的具体结果 |
| 前置任务 | 写具体任务编号和相对链接，或写无 / 外部条件 |
| 后续任务 | 写具体任务编号和相对链接，或写无 |
| 可并行任务 | 写具体任务编号、边界和共享资源约束，或写无 |
| 目标与来源 | 说明实现结果，并关联需求引用和实施方案 |
| 涉及位置 | 使用已核实路径、明确的“拟新增”路径或带原因的“待核实” |
| 操作步骤 | 写足以指导开发的具体动作，避免“完成后端开发”等空泛描述 |
| 交付物 | 实际代码、配置、文档或验证结果 |
| 完成条件 | 可观察、可检查的结果 |
| 验证方法 | 从项目核实的命令或具体人工检查步骤 |
| 状态 | 待开始 / 进行中 / 阻塞 / 已完成，并附必要证据或阻塞原因 |

规划阶段所有开发步骤默认“待开始”。步骤文件写完不等于开发完成，未运行的验证不得写成已通过。

前置任务和后续任务必须双向一致：如果 A 的后续任务包含 B，则 B 的前置任务必须包含 A。所有链接必须指向同一需求目录中的实际文件；没有前置或后续任务时明确写“无”。

## 6. 一致性与交付检查

第一阶段交付前检查：

- 每条范围内需求都有对应方案、拟执行范围和验收方式。
- 执行步骤生成建议覆盖完整实施范围，且说明预期顺序和依赖。
- 文件名符合 `{需求名}-实施计划.md` 规则。
- 文档状态为“待审核”，执行步骤生成状态为“未生成（待审核）”。
- 没有创建执行步骤文件，也没有把拟议编号写成正式任务。
- 假设、未验证事实、读取缺口和关键阻塞均显式标注。

第二阶段交付前检查：

- 每条范围内需求都有对应方案、执行步骤和验收方式。
- 每项步骤都有需求或实施方案依据，没有擅自增加功能。
- 每个任务文件名符合 `{需求名}-任务-T01-执行步骤.md` 规则。
- 任务编号全局唯一；文件名编号与正文编号一致。
- 所有前置、后续和可并行链接均可解析；前置与后续引用双向一致。
- 不存在缺失依赖或循环依赖。
- 所有执行步骤文件合起来覆盖完整实施范围，无矛盾、空隙或无意义重复。
- 文件名、相对链接、实施计划索引、任务编号和范围描述一致。
- 假设、未验证事实、读取缺口和关键阻塞均显式标注。
- 只有具备实际证据的开发结果或验证才能标记完成或通过。

第一阶段最终回复只链接实施计划，概述审核重点，并明确执行步骤尚未生成。第二阶段最终回复链接实施计划和所有执行步骤文件，简述拆分理由、推荐阅读或执行顺序、仍需用户决定的问题及真实验证状态。skill 的“完成”仅表示当前阶段规划文件已交付，不表示业务开发已完成。

## 7. 需求变更与跨会话续接

### 7.1 需求变更

1. 读取原始需求、用户补充说明、已有规划和当前代码状态。
2. 定位受影响的方案、执行步骤、依赖、风险和验收项。
3. 只修订受影响内容，保留用户手工修改及有效结论。
4. 将实施计划重新标记为“待审核”；存在执行步骤时将生成状态标记为“需重新生成”。
5. 在用户再次明确审核通过前，不新建或同步执行步骤。
6. 已完成步骤出现新增工作时，待再次审核通过后追加步骤或标记需重新验证，不抹去原有完成证据。
7. 默认不删除已有规划文件；范围变化导致文件被替代时，标明替代关系和新位置。

### 7.2 跨会话续接

先读取唯一实施计划的审核状态和执行步骤生成状态。待审核时只继续实施计划；只有用户在当前上下文中明确审核通过并要求生成执行步骤，才进入第二阶段。已有执行步骤文件时从实施计划索引读取，核对最新需求和项目状态，识别有效结论、阻塞和下一步。不要重新生成一套同名替代文档。

“继续完善实施计划”只更新实施计划且保持待审核；“生成执行步骤”要求明确的审核通过；“按执行步骤开发”是后续开发任务，必须遵守当时适用的文件修改与授权规则，不能因存在步骤文件而自动获得代码修改、提交、发布或部署权限。

旧的 `执行计划*.md` 文件可以作为历史规划读取，但新生成内容必须使用“实施计划”和“执行步骤”命名规则，不自动删除旧文件。

## 8. 授权与临时文件

- 第一阶段授权只允许创建或更新实施计划；不得借此生成执行步骤文件。
- 用户明确审核通过并授权第二阶段后，连续创建或更新全部执行步骤文件，不逐文件重复请求确认。
- 自动匹配 skill 不代表已取得写文件、业务开发或外部操作授权；遵守当前环境与项目的确认规则。
- 本 skill 不自动修改业务代码、提交、发布、部署、全局指令或个人 skill 安装目录。
- 临时转换、调研摘要和验证材料放到项目根目录的 `TEMP`，任务结束前只清理本次创建且可确认安全删除的对象。
- 需要跨会话保留过程资料时，说明路径、用途和保留原因。
