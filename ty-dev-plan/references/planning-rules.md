# 开发规划规则

本文件提供 `$ty-dev-plan` 的详细执行规则。生成或更新规划文件时阅读；仅判断 skill 是否适用时不必加载。

## 1. 输入与证据

### 1.1 确定输入

确认以下信息：

- 原始需求文档及其格式。
- 目标项目与适用的项目规范。
- 规划文件输出位置。
- 已有实施计划或执行计划（如有）。
- 实施计划当前审核状态，以及用户是否明确要求生成执行计划。

能从会话、项目或已有计划确定的信息不要重复询问。输出位置按以下顺序选择：用户明确指定的位置、项目已有约定、项目根目录下的 `docs/需求/{需求标识}/`。

原始需求是输入证据。不要生成新的需求说明文档，也不要擅自修改、覆盖或规范化原始需求文件。

### 1.2 读取不同格式

- Markdown：读取正文，并检查影响需求理解的相对链接、图片和附件是否可访问。
- DOCX：使用当前环境可用的文档读取能力提取正文和表格；图片、批注或修订会影响含义时必须核实。
- DOC：先识别真实格式，再使用环境已有的兼容读取或转换能力。需要转换时只在项目 `TEMP` 中创建副本，不覆盖原文件。
- 转换或解析失败：说明具体限制，请用户提供 DOCX 或 Markdown；不要宣称已完整读取。
- 关键图片、段落、表格或附件无法访问：记录为信息缺口，不得假定其中没有需求。

不要因扩展名相似而把 DOC 当作 DOCX。解析成功也不等于内容完整，应检查正文、表格及影响范围的视觉内容。

### 1.3 证据分类

在调研和文档中区分：

- 原文要求：来自需求文档或用户明确说明，使用原文编号或可定位引用。
- 已核实事实：来自实际代码、配置、测试或项目文档，附路径或其他证据。
- 建议方案：基于要求与事实形成的设计选择，说明理由。
- 假设：尚未确认但可暂时采用的可逆判断，明确影响。
- 待确认事项：会影响范围、业务规则、数据设计或总体方案的问题。

没有可访问的目标项目时，可以生成明确标注为概念性草稿的计划，但不得编造现有模块、文件路径、命令或验证结果。

## 2. 项目调研与澄清

先读取适用的项目指令、相关目录、核心实现、接口和测试约定。只调研与需求有关的范围；不要顺手修改业务代码或无关文件。

仅集中询问会改变功能范围、业务规则、数据设计或总体方案的关键问题。可逆细节可以采用有依据的建议，但必须写入假设。等待关键答案时继续调研不受影响的部分。

关键问题未解决时：

- 受影响章节标记为草稿或阻塞。
- 对应任务写明启动条件和阻塞原因。
- 不得声称整套计划已具备直接执行条件。

需求有编号时沿用原编号；没有编号时，可在实施计划中建立轻量引用编号，并映射到章节、标题、表格行或简短内容摘要。不要为编号另建需求文档。

## 3. 两阶段交付与审核门禁

### 3.1 第一阶段：只生成实施计划

首次处理一个需求时，只创建或更新唯一的 `实施计划.md`。不得同时创建执行计划，即使需求和项目上下文已经完整。

实施计划完成后：

- 将文档状态设为“待审核”。
- 将执行计划生成状态设为“未生成（待审核）”。
- 给出拟拆分的执行范围、顺序、启动条件和依赖，但不创建文件链接、不分配正式任务编号。
- 只向用户交付实施计划，指出重点审核项和待确认内容，然后停止。

用户要求评审、补充、修订或继续完善实施计划时，仍停留在第一阶段。每次实质修改后重新标记为“待审核”。

### 3.2 审核通过的判定

只有用户明确表达以下两层意图时，才进入第二阶段：

1. 最新实施计划已经审核通过。
2. 现在需要根据该计划生成执行计划。

不得根据以下情况推断审核通过：

- 用户没有提出异议。
- 实施计划内容看起来完整。
- 用户只说“继续”“完善”“修改这里”或提出评审意见。
- 项目中已经存在旧执行计划。

如果用户明确审核通过但没有要求生成执行计划，记录审核状态并等待；如果用户要求生成执行计划但无法确认实施计划是否已审核通过，先请求确认审核结果。

### 3.3 第二阶段：生成执行计划

进入第二阶段时：

1. 重新读取最新实施计划，不能依赖审核前的会话记忆。
2. 识别用户在审核中直接修改或补充的内容，并将其视为最新方案的一部分。
3. 核对相关项目事实是否发生变化；有冲突时说明，不擅自改写已审核方案。
4. 按实施计划中的拆分建议和实际依赖生成一份或多份执行计划。
5. 更新实施计划中的执行计划索引、正式任务编号、覆盖关系和生成状态。
6. 连续生成本阶段所需的全部执行计划，不逐文件重复请求授权。

## 4. 唯一实施计划

每个需求只维护一个主实施计划，默认命名为 `实施计划.md`。它必须包含：

1. 文档状态、需求来源、目标项目和可获得的调研基准。
2. 实施目标、包含范围和明确不包含的内容。
3. 项目现状、相关实现、约束和可复用能力，附已核实路径。
4. 推荐技术方案、关键决策和理由；只在存在实质选择时讨论替代方案。
5. 模块及文件变更、接口与数据变化、关键业务流程及适用的异常和边界处理。
6. 按需求实际需要补充的兼容、迁移或回退安排。
7. 验证策略和可观察的验收依据。
8. 假设、风险和待确认事项。
9. 第一阶段记录执行计划拆分建议、范围、依赖和推荐顺序；第二阶段更新为实际文件索引。
10. 第一阶段记录需求到实施方案、拟执行范围及验证方式的覆盖关系；第二阶段补充正式任务编号。

路径必须标明证据状态：已存在且核实的路径直接引用；计划创建的路径写成“拟新增”；不能确认的位置写成“待核实”并说明原因。

已有实施计划时先完整读取，保留用户手工补充和仍有效的结论，在原文件上定向修订。不要默认创建“最终版”“最终版2”等并行主文档。

实施计划状态使用“待审核 / 审核通过 / 已替代”。另行记录执行计划生成状态：“未生成（待审核）/ 待生成（已审核）/ 已生成 / 需重新生成”。第一阶段不能因为尚无执行计划而把实施计划标为不完整。

## 5. 执行计划拆分

### 4.1 是否拆分

以下情况通常使用一份 `执行计划.md`：工作量较小、任务依赖紧密、可以作为一次交付整体验证。

存在以下特征时，可拆成 `执行计划-01-{范围}.md` 等多份文件：

- 有明确阶段或可独立验收的模块。
- 需要分批实施或交接。
- 不同范围具有清晰启动条件和交付边界。

不要按固定任务数强行拆分，也不要机械地按前端、后端拆分。必须共同完成或共同验证的紧密耦合任务尽量放在同一份计划。多份计划必须在实施计划中全部登记；独立任务可标注可并行，但不得因此自动启动子智能体。

### 4.2 每份计划的内容

每份执行计划说明：

- 来源实施计划。
- 本计划负责和不负责的范围。
- 启动条件、前置计划、后续计划和跨计划依赖。
- 任务清单及其内部顺序。
- 整份计划的完成条件和验收方式。

### 4.3 每项任务的最低信息

| 字段 | 规则 |
| --- | --- |
| 任务编号 | 整个需求范围内唯一，例如 `T-001`；不依赖文件名区分 |
| 目标与来源 | 说明实现结果，并关联需求引用和实施方案 |
| 前置依赖 | 写具体任务编号或外部条件；跨文件依赖注明计划 |
| 涉及位置 | 使用已核实路径、明确的“拟新增”路径或带原因的“待核实” |
| 操作步骤 | 写足以指导开发的具体动作，避免“完成后端开发”等空泛描述 |
| 交付物 | 实际代码、配置、文档或验证结果 |
| 完成条件 | 可观察、可检查的结果 |
| 验证方法 | 从项目核实的命令或具体人工检查步骤 |
| 状态 | 待开始 / 进行中 / 阻塞 / 已完成，并附必要证据或阻塞原因 |

规划阶段所有开发任务默认“待开始”。计划写完不等于开发任务完成，未运行的验证不得写成已通过。

## 6. 一致性与交付检查

第一阶段交付前检查：

- 每条范围内需求都有对应方案、拟执行范围和验收方式。
- 拆分建议覆盖完整实施范围，且说明预期顺序和依赖。
- 文档状态为“待审核”，执行计划生成状态为“未生成（待审核）”。
- 没有创建执行计划文件，也没有把拟议编号写成正式任务。
- 假设、未验证事实、读取缺口和关键阻塞均显式标注。

第二阶段交付前检查：

- 每条范围内需求都有对应方案、任务和验收方式。
- 每项任务都有需求或实施方案依据，没有擅自增加功能。
- 任务编号全局唯一；所有依赖均可解析，不存在缺失依赖或循环依赖。
- 所有执行计划合起来覆盖完整实施范围，无矛盾、空隙或无意义重复。
- 文件名、相对链接、计划索引、任务编号和范围描述一致。
- 假设、未验证事实、读取缺口和关键阻塞均显式标注。
- 只有具备实际证据的开发结果或验证才能标记完成或通过。

第一阶段最终回复只链接实施计划，概述审核重点，并明确执行计划尚未生成。第二阶段最终回复链接实施计划和所有执行计划，简述拆分理由、推荐阅读或执行顺序、仍需用户决定的问题及真实验证状态。skill 的“完成”仅表示当前阶段规划文件已交付，不表示业务开发已完成。

## 7. 需求变更与跨会话续接

### 6.1 需求变更

1. 读取原始需求、用户补充说明、已有规划和当前代码状态。
2. 定位受影响的方案、拆分建议、任务、依赖、风险和验收项。
3. 只修订受影响内容，保留用户手工修改及有效结论。
4. 将实施计划重新标记为“待审核”；存在执行计划时将生成状态标记为“需重新生成”。
5. 在用户再次明确审核通过前，不新建或同步执行计划。
6. 已完成任务出现新增工作时，待再次审核通过后追加任务或标记需重新验证，不抹去原有完成证据。
7. 默认不删除已有计划文件；范围变化导致文件被替代时，标明替代关系和新位置。

### 6.2 跨会话续接

先读取唯一实施计划的审核状态和执行计划生成状态。待审核时只继续实施计划；只有用户在当前上下文中明确审核通过并要求生成执行计划，才进入第二阶段。已有执行计划时从索引读取，核对最新需求和项目状态，识别有效结论、阻塞和下一步。不要重新生成一套同名替代文档。

“继续完善实施计划”只更新实施计划且保持待审核；“生成执行计划”要求明确的审核通过；“按计划执行开发”是后续开发任务，必须遵守当时适用的文件修改与授权规则，不能因存在计划而自动获得代码修改、提交、发布或部署权限。

## 8. 授权与临时文件

- 第一阶段授权只允许创建或更新实施计划；不得借此生成执行计划。
- 用户明确审核通过并授权第二阶段后，连续创建或更新全部执行计划，不逐文件重复请求确认。
- 自动匹配 skill 不代表已取得写文件、业务开发或外部操作授权；遵守当前环境与项目的确认规则。
- 本 skill 不自动修改业务代码、提交、发布、部署、全局指令或个人 skill 安装目录。
- 临时转换、调研摘要和验证材料放到项目根目录的 `TEMP`，任务结束前只清理本次创建且可确认安全删除的对象。
- 需要跨会话保留过程资料时，说明路径、用途和保留原因。
