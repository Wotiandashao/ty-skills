# 需求开发规划

把用户提供的需求文档转换为基于真实项目的两阶段开发规划：先交付唯一实施计划供用户审核；只有用户明确审核通过后，才按任务拆分生成一组独立的执行步骤文件。

不生成需求说明文档，不修改原始需求，不自动修改业务代码、提交、发布或部署。

## 输入

需要以下输入：

- 用户提供的 `.md`、`.docx` 或 `.doc` 需求文档。
- 可访问的目标项目，或用户明确说明当前只能生成概念性草稿。
- 可选的输出位置、既有实施计划和执行步骤，以及实施计划的审核状态。

从上下文或项目可以确定的信息不要重复询问。若用户未指定输出位置，优先沿用项目现有约定，否则使用项目根目录的 `docs/需求/{需求标识}/`。

## 工作流

### 1. 读取需求和项目

读取需求正文、表格，以及影响需求理解的图片、批注、修订、引用或附件。Word 输入使用当前环境可用的文档读取能力；旧版 DOC 无法可靠读取时，说明限制并请求 DOCX 或 Markdown，绝不假装已读取完整内容。

读取适用的项目指令，并调研与需求有关的目录、实现、接口、配置和测试。不要扩大到无关代码。

生成或更新规划前，阅读 [开发规划规则](references/planning-rules.md)，按其中的证据分类、输入处理和授权边界执行。

### 2. 澄清关键缺口

区分原文要求、已核实项目事实、建议方案、假设和待确认事项。仅对会改变功能范围、业务规则、数据设计或总体方案的问题集中提问；可以继续完成不受影响的调研。

若关键问题仍未解决，将受影响内容明确标记为草稿或阻塞，不声称计划可直接执行。没有可访问项目时，不编造模块、路径、命令或验证结果。

### 3. 第一阶段：编写唯一实施计划

使用 [实施计划模板](assets/implementation-template.md) 创建或更新 `{需求名}-实施计划.md`。实施计划应覆盖范围、项目现状、推荐方案、变更位置、接口与数据、关键流程、适用的兼容或回退、验证策略、风险、待确认事项、执行步骤生成建议和需求覆盖关系。

已有实施计划时先完整读取并定向修订，保留用户手工修改和仍有效的结论。不要创建并行的“最终版”主文档。

首次生成或任何审核修改完成后，将实施计划标记为“待审核”，只交付该文件并停止。此阶段不得创建、更新或补全执行步骤，也不得提前把拟议任务编号当作正式执行任务。

### 4. 等待实施计划审核

最终回复链接实施计划，概括需要用户重点审核的方案、假设和待确认事项，并明确说明尚未生成执行步骤。

用户要求评审、补充或修改实施计划时，只更新实施计划并继续等待审核。普通的“继续”“完善一下”或对局部内容的讨论，不视为审核通过。

只有用户明确表示实施计划已经审核通过，并要求生成执行步骤，才进入下一阶段。审核通过是执行步骤生成的必要门禁，不能根据文档看起来完整或用户未提出异议而推断。

### 5. 第二阶段：拆分并编写执行步骤

收到明确审核通过通知后，重新读取用户修改后的最新实施计划和相关项目状态，以审核后的实施计划为方案依据。若实施计划包含用户修改，必须保留并反映到执行步骤中。

根据交付边界、依赖关系和独立验收能力拆分正式任务；不按固定数量或技术层机械拆分。使用 [执行步骤模板](assets/execution-step-template.md) 为每项任务创建一个独立文件：

- 实施计划文件：`{需求名}-实施计划.md`。
- 任务文件：`{需求名}-任务-T01-执行步骤.md`、`{需求名}-任务-T02-执行步骤.md` 等。

需求名用于所有同一需求的文件名；文件名中的非法字符应清理，但正文保留完整需求名称。任务编号在整个需求中保持唯一，使用 `T01`、`T02` 等格式。每个任务文件必须写明前置任务、后续任务、可并行任务、来源、涉及位置、具体动作、交付物、完成条件、验证方法和状态。规划阶段默认“待开始”，未执行的验证不得标记为已通过。

在第二阶段的授权范围内，连续生成全部执行步骤文件，不要求用户逐文件下达指令。生成后同步更新实施计划中的执行步骤索引、正式任务编号和覆盖关系。可并行的任务只在步骤文件和实施计划中标注，不自动调度子智能体。

### 6. 检查并交付

第一阶段检查需求、方案和验收方式是否对应，以及执行步骤生成建议是否覆盖实施范围；不以缺少执行步骤文件或正式任务编号为错误。第二阶段再检查需求、方案、任务和验收方式是否完整对应，并检查文件名、任务编号、前置任务、后续任务、相对链接和执行顺序是否一致且无循环依赖。模板中的字段必须填写、删除，或说明为何待确认，不能留下无解释的占位内容。

第一阶段最终回复只提供实施计划链接和审核重点。第二阶段最终回复提供实施计划及全部执行步骤文件的链接，说明拆分理由、推荐顺序、待用户决定的问题和实际验证状态。清理本次创建的临时文件；只保留确有跨会话用途的过程资料并说明原因。

## 变更与续接

需求或实施方案变化时，读取原始需求、补充说明、现有规划和最新项目状态，只修改受影响内容并保留用户手工内容。实施计划发生实质修改后重新标记为“待审核”，在用户再次明确审核通过前不生成或同步执行步骤；已有执行步骤保留但标明需要重新同步，不抹去完成证据。

跨会话继续时，先读取实施计划的审核状态和执行步骤生成状态：待审核则继续第一阶段；用户明确确认审核通过后才进入第二阶段；已有执行步骤文件时再从索引读取并核对。不要把“继续完善计划”当成审核通过，也不要把“生成执行步骤”当成“按步骤修改业务代码”。

## 权限边界

skill 的自动匹配不等于获得写文件、跳过实施计划审核或开展业务开发的权限。遵守当前适用的项目规则和用户授权；若规则要求修改前确认，先给出具体文件计划并取得同意。实施计划和执行步骤分阶段授权，业务代码修改、安装、提交、发布、部署或全局配置变更仍需各自明确授权。
